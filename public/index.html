Webhook Verification

Verify incoming inventory events before they enter the system.

POST /webhook/inventory
Algorithm HMAC-SHA256
Header X-Webhook-Signature

Every incoming webhook is authenticated server-side using a shared secret and HMAC-SHA256. The signature is compared with timing-safe equality to prevent side-channel attacks.

TEST SCENARIOS
01
Valid Signature
Correct payload + Correct signature = HTTP 200
Server recomputes HMAC using the shared secret and the exact raw bytes received. Digests match — webhook accepted.
02
Invalid Signature
Incorrect signature = HTTP 401
Signed with the wrong secret. HMAC digests differ — webhook rejected immediately.
03
Modified Payload
Original signature + Modified payload = HTTP 401
Changing one byte in the body produces a completely different HMAC. The original signature no longer matches.

WHY VERIFICATION MATTERS
Without Verification
Anyone can POST to the endpoint and inject fake inventory updates. There is no way to know if the request came from the real warehouse system.

HOW THIS DASHBOARD RECEIVES UPDATES Two techniques keep the page in sync with the server
🔄 Polling GET /api/status

The browser asks the server "are you still alive?" on a fixed timer. Every 8 seconds the dashboard fires a GET /api/status request and updates the SERVER ONLINE / OFFLINE badge in the header.

Browser
→ every 8 s →
GET /api/status
←
{ status: "ok" }
✓ Simple — just a regular fetch()
✗ Fires requests even when nothing changed
✗ Adds a delay equal to the poll interval
📡 Server-Sent Events (Push) GET /api/events

The browser opens one persistent connection to GET /api/events and leaves it open. The server pushes a new event line whenever a webhook arrives — no repeated requests needed. That is how the Recent Events table below updates instantly.

Browser
— open once →
GET /api/events
← event pushed
data: {…}
✓ Instant — no waiting for the next poll tick
✓ Efficient — only one long-lived connection
✗ Slightly more complex server setup
